# VER02｜財務、業務和 AI 算出的營收不同，誰才是對的？

**問題分類：** 財務與數據分析  
**探索狀態：** 固定合成資料 PoC 已解決，最終人工驗收待完成  
**案例類型：** AI 商業問題解決案例

## 案例概覽

假設你是一家電商公司的老闆，想知道上個月的營收。

財務部門告訴你：100 萬元。

業務部門說：120 萬元。

電商後台顯示：135 萬元。

公司新導入的 AI 報表則算出：128 萬元。

四個數字，到底誰才是對的？

答案可能是：沒有人算錯。

財務可能依照會計收入認列規則計算，業務看的是成立訂單金額，電商後台顯示交易總額，而 AI 使用了另一套篩選條件。

每個數字都有自己的計算依據，卻不一定在回答同一個問題。

如果公司連「營收」的定義都沒有確認，AI 即使把每一筆資料加總得毫無誤差，也可能交出老闆不想看的數字。

**在問 AI 算得對不對之前，先確認公司到底要它算什麼。**

# 商業視角｜Business View

## 01｜四個營收數字，可能都沒有算錯

企業裡經常存在不同版本的營收數字。

財務部門關心的是符合會計規則的收入。

業務部門可能更重視訂單成交金額。

電商後台可能顯示消費者下單時的交易總額。

這些數字不一定相同，也不一定有誰算錯。

真正的問題可能是：每個部門使用的指標定義不同。

例如，一張訂單已經成立，但客戶尚未付款。

業務可能認為這筆訂單應該計入業績；財務則可能依照收入認列規則，不在同一時間將它列入收入。

如果 AI 使用另一套篩選條件，就可能產生第四個數字。

這裡不是要判斷哪個部門應該改用同一種算法，而是要確認每個數字究竟代表什麼。

因為**數字計算正確，不代表它回答了正確的問題。**

開頭的跨部門營收差異是用來說明問題的假設情境，不是真實企業案例，也不是本次實驗的測試結果。

## 02｜先決定要算什麼，才能知道有沒有算對

在 VER02 中，我們針對這個問題建立了一個小型實驗。

但這次沒有實際測試 AI 自動產生營收報表，也沒有模擬不同部門協調指標定義的過程。

我們真正測試的是：

**當企業已經確認計算規則，能不能用另一套程序，找出不符合規則的計算結果？**

首先建立八張模擬電商訂單，包含付款、取消、退款、跨月份與外幣交易。

接著，事先確定一套計算規則：

計算 2026 年 11 月付款成功、未取消的訂單金額，不含稅金與運費，扣除月底前完成的退款，外幣則按照約定匯率換算為台幣。

依照這套規則，正確結果是 **440 元**。

這裡計算的是「訂單淨額」，不是正式會計上的營收。

兩者可能有不同的認列條件，不能混為一談。

有了明確定義，我們才有辦法判斷後續產生的數字究竟對不對。

## 03｜640 元也可能是「正確算出來的錯誤答案」

我們刻意準備了幾種計算錯誤。

例如，一張已經取消的訂單，原本不應計入，卻被加進總額。

結果從 440 元變成 **640 元**。

如果忘記扣除退款，結果會是 **520 元**。

如果資料處理方式造成同一張訂單被重複加總，甚至會得到 **840 元**。

這些都是實驗中刻意設計的錯誤，並不是 AI 模型自行犯下的錯誤。

以 640 元為例，程式的加法可能完全正確。

它只是把一張不該計入的訂單也算進去了。

重新執行同一套公式，仍然會得到 640 元。

問題不在加法，而在計算範圍不符合原先約定的規則。

這也是為什麼企業不能只看報表能不能成功產生，或數字能不能重複算出來。

還需要確認：

**哪些資料被納入、哪些被排除，以及退款和匯率的處理是否符合定義。**

## 04｜這次不需要另一個 AI，傳統程式就能檢查

我們沒有讓另一個 AI 模型來判斷數字是否正確。

這個原型採用固定程式進行計算與驗證。

AI Coding Agent 參與了程式開發，但這次測試的重點不是 AI 模型的計算能力。

做法是先保存已確認的計算規則，讓計算程序交出總額與逐筆明細，再由另一套驗證程序根據原始訂單資料核對。

例如，驗證程序會檢查取消訂單是否被排除、退款是否正確扣除，以及不同幣別是否按照規則換算。

如果符合規則，就通過。

發現錯誤，就拒絕。

如果缺少必要資料或規則尚未確認，就要求人工處理，而不是勉強放行。

最後，我們測試了五種刻意設計的錯誤：

- 納入取消訂單。
- 重複加總。
- 漏扣退款。
- 混用不同幣別。
- 扣除截止時間後才完成的退款。

**五種錯誤全部被驗證程序攔截。**

這個結果說明，在本次規則明確、資料量很小的測試中，傳統程式就能完成有效的核對，不必再引入一個 AI 模型。

但這不代表所有企業報表都能用同樣方式解決。

真實環境可能涉及更複雜的資料來源、例外情況與經常變動的業務規則。

## 05｜回到老闆的四個營收數字

假設財務、業務、電商後台與 AI 都能提供完整的計算明細，而且每個數字都通過了各自的計算檢查。

那麼，誰才是對的？

這時候，單純檢查加總已經無法回答問題。

老闆必須先確認自己要看的是成立訂單總額、扣除退款後的訂單淨額，還是符合會計收入認列條件的金額。

不同指標可以同時存在，也可能都正確。

企業不一定需要把所有部門的數字統一成同一個數字，而是要讓每個數字都有清楚的名稱、定義與用途。

否則，即使 AI 產生的報表沒有任何計算錯誤，仍然可能被拿來回答不適合的經營問題。

## 06｜企業導入 AI 報表，先確認三件事

### 第一，重要指標有沒有明確、經過確認的定義？

例如營收是否包含取消訂單、退款算在哪個月份、跨幣別如何換算。

這些規則應該由理解業務的人確認，而不是讓 AI 自行猜測。

### 第二，數字能不能追查來源？

除了總額，還要能核對使用了哪些資料、排除了哪些紀錄，以及計算過程如何處理例外情況。

### 第三，計算結果有沒有適當的驗證方式？

對規則固定的指標，可以先評估傳統程式能否完成檢查。

遇到資料缺漏或定義不明時，應該保留人工確認的機制，而不是因為系統成功產生報表就直接採用。

這三件事不一定需要複雜的 AI 治理系統，但需要企業清楚分配指標定義、資料管理與結果確認的責任。

## 重點收穫｜Key Takeaways

**1. 數字一致，不代表業務定義正確。**

如果兩套計算使用相同的錯誤規則，即使結果完全一致，也可能都不符合企業真正需要的指標。

**2. 驗證必須回到原始資料與已確認的規則。**

除了最後總額，還要檢查資料範圍、訂單狀態、退款、匯率與其他重要計算條件。

**3. 不一定需要用另一個 AI 來驗證 AI。**

在本次規則明確的小型測試中，傳統程式就成功攔截了五種刻意設計的計算錯誤。

**4. 不同部門的數字可以不同，但定義必須清楚。**

企業應該確認每個指標的名稱、計算方式與用途，而不是要求所有報表都產生同一個數字。

**核心收穫：在問 AI 算得對不對之前，先確認公司到底要它算什麼。**

# 技術視角｜Technical View

## 01｜技術方法

VER02 使用合成電商訂單資料，比較兩種驗證方式。

第一種是沿用原本公式重新計算。

第二種則根據事先確認的業務定義，使用另一套計算邏輯重新核對原始資料。

研究的核心不是讓 AI 模型直接計算，而是建立候選結果與驗證結果分離的流程。

### A. Same-formula Recalculation

第一種方法是同公式重算。

它沿用 Worker 選擇的篩選條件與計算公式，再計算一次，確認結果是否一致。

這種方式能發現部分計算或執行不一致的問題。

但如果原本的公式就錯了，重新計算也可能得到相同的錯誤答案。

例如，Worker 忘記排除取消訂單，重算程式也沿用相同篩選條件，兩者就可能一致地算錯。

### B. Definition-based Verification

第二種方法不直接相信 Worker 使用的公式。

我們先固定經人類確認的業務指標定義，再讓 Verifier 根據定義、原始資料及逐筆訂單重新計算參照結果。

Verifier 會檢查：

- 訂單是否符合期間與狀態條件。
- 是否正確處理取消與退款。
- JOIN 是否造成重複加總。
- 幣別與匯率是否正確。
- 金額精度及四捨五入是否符合規則。
- 必要資料與定義是否完整。

兩種方法最大的差異是：

**Baseline 檢查「是否算得一樣」；Verifier 檢查「是否符合已確認的業務定義」。**

### C. Worker 與 Verifier 分離

本次使用兩套不同的程式邏輯。

Worker 負責根據訂單資料產生候選金額與逐筆明細。

Verifier 不直接採用 Worker 的公式，而是依據固定的業務定義與原始資料重新核對。

Verifier 最後給出三種狀態：

| 狀態 | 意義 |
|---|---|
| PASS | 必要檢查通過，允許輸出可信總額 |
| FAIL | 已確認違反定義或驗證條件 |
| REVIEW | 必要資訊缺失或定義尚未確認 |

如果結果是 FAIL 或 REVIEW，可信總額保持空值。

Worker 即使自行宣稱 PASS，也不能改變 Verifier 的判定。

這裡的分離是計算邏輯與判定來源的分離，不代表 Worker 與 Verifier 由不同開發者建立，或具備完整的系統權限隔離。

## 02｜使用技術與工具

| 技術／工具 | 本次用途 |
|---|---|
| Python | 建立 Worker、Verifier 與實驗流程 |
| SQLite | 保存合成訂單資料，供 Worker 查詢 |
| SQL | 執行訂單篩選及彙總 |
| Python Decimal | 處理金額精度與四捨五入 |
| JSON | 保存業務定義、驗收情境與結果 |
| SHA-256 | 核對指定檔案及定義版本是否一致 |
| pytest | 執行功能、安全與治理測試 |

本次使用 Python 標準函式庫完成主要實作，沒有新增付費 API 或模型服務。

研究重點是驗證架構，不是比較不同 LLM 的計算能力。

## 03｜實作流程

### 步驟一：固定訂單淨額的定義

首先確認本次要計算的指標：

2026 年 11 月付款成功、未取消的訂單，扣除這批訂單在月底前完成的退款，排除稅與運費，並統一換算為新台幣。

退款使用原訂單匯率，金額依約定精度進行四捨五入。

這是本次實驗的訂單淨額定義，不等同正式會計營收。

使用者確認指標口徑後，才建立測試資料與參照答案。

### 步驟二：建立合成資料與標準答案

本次資料包含：

- 8 張訂單。
- 10 筆訂單明細。
- 3 筆退款。
- 1 筆假設匯率資料。

其中符合條件的訂單換算後合計為 520.00 TWD，截止日前退款為 80.00 TWD。

因此，固定基準答案為：

**520.00 − 80.00 = 440.00 TWD**

這個答案經過算術交叉核對，但審查者事先知道候選答案，因此不能宣稱完成盲審。

### 步驟三：Worker 產生候選分析

Worker 使用 SQLite 查詢資料，並以 Decimal 處理金額，產生候選總額與逐單明細。

研究另外設計五種故意出錯的計算模式，模擬常見的業務邏輯錯誤。

這些錯誤是刻意注入的，不是觀察到 AI 自然犯錯的頻率。

### 步驟四：Verifier 根據定義重新核對

Verifier 不使用 Worker 提交的公式作為判斷權威。

它從固定位置讀取已確認的定義、資料及基準，先檢查必要資訊與定義一致性，再用另一套 Python 逐單計算邏輯產生參照結果。

最後根據核對結果，產生 PASS、FAIL 或 REVIEW。

整體流程為：

**原始訂單資料 + 已確認指標定義 → Worker 候選結果 → Verifier 獨立核對 → PASS / FAIL / REVIEW**

如果結果是 FAIL 或 REVIEW，就不輸出可信總額。

這樣可以區分「系統算出一個數字」與「這個數字已經通過指定驗證」。

### 步驟五：測試錯誤與例外情境

本次測試五種刻意注入的業務邏輯錯誤：

| 錯誤類型 | 錯誤候選金額 | 定義驗證 |
|---|---:|---|
| 納入取消訂單 | 640.00 TWD | FAIL |
| JOIN 重複加總 | 840.00 TWD | FAIL |
| 漏扣退款 | 520.00 TWD | FAIL |
| 混用原幣金額 | 208.00 TWD | FAIL |
| 扣除截止後退款 | 430.00 TWD | FAIL |

在這五個固定錯誤案例中，同公式重算全部得到數值一致的結果。

但 Definition-based Verifier 成功拒絕了全部五個錯誤候選。

另外，本次固定 11 個驗收情境，涵蓋正常計算、精度、錯誤候選、資料缺漏、定義確認與指定唯讀連線等條件。

全部 11 個情境符合預期。

其中：

- 正常案例得到 PASS，可信總額為 440.00 TWD。
- 精度邊界案例得到 PASS，金額為 200.06 TWD。
- 五個錯誤候選全部得到 FAIL。
- 缺少必要匯率或定義未確認時，得到 REVIEW，且不輸出可信總額。

這些結果支持本次固定合成資料與指定驗收條件下的實作有效，但不能直接推論到真實企業的所有財務資料情境。

## 重點收穫｜Key Takeaways

**1. 重算不等於驗證。**

如果兩個計算流程使用相同的錯誤定義，即使數字完全一致，也可能都不符合業務需求。

**2. 驗證應以已確認的業務定義為依據。**

除了總額，還需要檢查期間、訂單狀態、資料粒度、退款、幣別與金額精度。

**3. 候選結果與可信結果需要分開。**

Worker 可以提出金額，但不能自行決定是否通過驗證。必要資料缺失或定義不明時，系統應保留 REVIEW 狀態。

**4. 程式邏輯分離，不代表已完成完全獨立的驗證。**

本次 Worker 與 Verifier 雖然使用不同計算邏輯，仍由同一個 AI Coding Agent 參與開發，可能共享相同的錯誤假設。

**核心收穫：驗證 AI 分析結果時，不能只問「數字有沒有算對」，還必須問「它是不是按照正確的業務定義算出來的」。**

## 案例範圍與限制

本案例使用 8 張合成訂單、10 筆訂單明細、3 筆退款及 1 筆假設匯率資料。

在固定合成資料與 11 個驗收情境內，所有測試符合預期，五種刻意設計的錯誤計算也全部被驗證程序攔截。

本輪三階段實驗已完成，並在固定合成資料 PoC 的範圍內判定為 Solved，但最終人工驗收仍待完成。

Worker、Verifier、資料與測試由同一個 AI Coding Agent 參與編製，尚未完成完全獨立的盲測。

本次沒有使用真實企業資料，也沒有建立完整權限隔離、不可竄改稽核紀錄，或驗證企業實際導入成本與效益。

因此，本案例展示的是明確業務定義下的計算驗證方法，不代表已證明所有企業營收或財務報表都能透過相同方式可靠驗證。
